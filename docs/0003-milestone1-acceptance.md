# Milestone 1 Docker acceptance

Date: 2026-10-19. Status: implementation and local acceptance complete.
Milestone 2 has not been started. No application or Docker code fixes were needed
for this verification; only the documentation and plan status changed.

## Environment

- macOS ARM64 host, Python 3.13.5, uv 0.13.1.
- Docker Desktop 4.95.0, Docker Engine 29.8.2, Compose v5.6.0.
- Linux ARM64 API image, Python 3.13.16, non-root UID/GID 10001.
- PostgreSQL 17.11 and Redis 7.4.11, using the checked-in Compose release tags.

Docker Desktop's bundled CLI directory was added to PATH for commands below.
Docker socket access and localhost requests required sandbox approval. Local
credentials were generated by the setup script; none were printed or committed.

## Build, startup, migration, and connectivity

The documented command succeeded from the repository root:

```sh
sh scripts/dev.sh
```

It built both API and migration images from the lockfile, initialized a new
PostgreSQL named volume, ran the migration job with exit code 0, and waited for
PostgreSQL, Redis, and API health checks to pass. Ports are published on localhost.
The API runs as `queuepilot`, UID/GID 10001, confirmed using `exec api id`.

The following checks also passed:

```sh
docker compose --env-file .env.compose ps -a
docker compose --env-file .env.compose exec -T api alembic current
docker compose --env-file .env.compose exec -T api alembic check
docker compose --env-file .env.compose exec -T postgres pg_isready -U queuepilot -d queuepilot
docker compose --env-file .env.compose exec -T redis redis-cli ping
```

Alembic reported `0001_foundation (head)` and no new upgrade operations.
PostgreSQL accepted connections; Redis returned `PONG`. A Python check inside
the API container used its actual configured async clients to verify PostgreSQL
`SELECT 1`, the expected Alembic revision, UTC timezone, and Redis PING. This
verified service-to-service connectivity using the application's configuration.

## HTTP and outage behavior

Host HTTP checks asserted status codes and exact JSON responses:

| Condition | Endpoint | Result |
| --- | --- | --- |
| Healthy | `/` | 200, `{"message":"Welcome to QueuePilot"}` |
| Healthy | `/health/live` | 200, `{"status":"ok"}` |
| Healthy | `/health/ready` | 200, ready/database ok/Redis ok |
| Healthy | `/docs` | 200, Swagger UI page |
| Redis stopped | `/health/ready` | 200, degraded/database ok/Redis unavailable |
| PostgreSQL stopped | `/health/ready` | 503, not_ready/database unavailable/Redis ok |
| Both stopped | `/health/ready` | 503, both dependencies unavailable |
| Both stopped | `/health/live` and `/` | 200 |
| Dependencies restarted | `/health/ready` | Recovered to 200, ready, without restarting API |

Only this newly started development stack's dependency containers were stopped.
They were restored in cleanup. PostgreSQL's baseline persisted across restart.
Responses contained only the documented statuses, with no raw errors or URLs.

The happy-path smoke commands are:

```sh
curl --fail http://127.0.0.1:8000/
curl --fail http://127.0.0.1:8000/health/live
curl --fail http://127.0.0.1:8000/health/ready
```

## Quality and isolated integration tests

Separate ephemeral test services were started using the documented command:

```sh
docker compose --env-file .env.compose --profile test up -d --wait postgres-test redis-test
```

A new host virtual environment was installed with `uv sync --locked`. Ruff lint,
Ruff format checking, and strict mypy over `src tests scripts migrations` passed.
`uv run --locked python scripts/test_integration.py` passed all **42 tests**, with
no skips, against those Docker test services.

The same quality/test gates were then run in a disposable Linux container based
on the built API image. Tests and scripts were mounted read-only, development
dependencies were installed from the lockfile, and explicit test URLs pointed
to the separate test containers through the Compose network:

```sh
sh scripts/check.sh --require-integration
```

Result: locked sync, Ruff lint/format, strict mypy, and **42 tests passed** on
Linux/Python 3.13.16. This transient verifier used root to install development
tools; the normal API and migration containers use UID 10001.

Coverage includes startup/shutdown, required/invalid configuration, initial
migration from empty databases, repeated head upgrades, stale/unmigrated schema
rejection, commit/rollback, real-service probes, and a separate HTTP server process.
Only UUID-suffixed databases created on the dedicated test server were dropped.
